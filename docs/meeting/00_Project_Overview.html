Staffware on the web

Republic Electric West · Project overview: how the system runs and how the modules work together
Staffware replaces the Microsoft Access screens with a web application. It works on the same SQL Server database and the same logins as today, so no data is moved and Access can keep running side by side while teams switch over, module by module.

1. How the system runs

1. BrowserStaff open the Staffware address in Chrome, Edge or Safari. Nothing is installed on their PCs. They see menus, forms, lists and reports.
→
2. Staffware serverChecks who is logged in and which modules that person may use, applies the same business rules as the Access version, then reads or saves data.
→
3. SQL Server databaseThe existing Staffware database. Every form, record and posting is stored here, exactly where Access stores it today.
Microsoft Access (existing)Keeps working against the same database during the roll-out. A record saved in the web app appears in Access, and the other way round.

What happens when someone uses a screen

  • Sign in: with the existing Staffware login. The system opens only the modules that login is allowed to use. If a module is switched off for a person, its screens and data are refused, not only hidden.
  • Open a list or report: the browser asks the server, the server reads the database and returns the rows. Lists can be searched, sorted and paged; reports can be exported to CSV and printed.
  • Enter or change data: the form checks the entries, the server checks them again, then saves them. Important multi-step actions (post payroll, post billing, transfer a bid) are saved all or nothing, so a failure never leaves half-posted data.
  • Delete or post: the person is asked to confirm first, and many actions show a preview of what will change.
  • Every record keeps who entered it and when, the same as Access.

Security in plain words

  • Login creates a private session that scripts and browser tools cannot read; signing out ends it on the server.
  • Access is re-checked continuously: deactivating a login or removing a module takes effect within about half a minute.
  • Only the Staffware screens can talk to the server; copied addresses, other websites and tools such as Postman are refused.
  • Repeated wrong passwords lock the account for 15 minutes. Error messages never show internal details.
  • The program code delivered to the browser is scrambled so it cannot be read in developer tools.

4. What every module has in common

  • Same look and behaviour: a menu on the left grouped by area, a search box that finds accounts, jobs, lots, employees and items (Ctrl+K), and tabs inside each module.
  • Lists: search, sort, page through, click a row to open it, export to CSV where it makes sense.
  • Forms: required fields are marked; pick-lists depend on each other (builder, then job, then phase, then lot); Save, Cancel and Delete work the same everywhere; delete and post actions ask for confirmation.
  • Reports: pick a report, choose the filters it needs, see the result on screen, then export or print.
  • Division filter: the top bar can limit the dashboard to one division (REI or REW).
  • Dashboard: the home page shows open lots, payroll pending, inventory value, items that need attention, billing by month and recent activity, with a link into each module.

5. Where the project stands and next steps

  • All 18 modules are built and work on the same database. They were built from the Access forms, macros and queries so the same business rules apply.
  • Accounts Receivable and Contract Management have been compared button by button with the Access switchboard, and each has a separate map showing every Access button and where it lives in the web app.
  • For the other modules, a button-by-button comparison with Access is the next step. Where Access reports or exports are not yet built (for example some Inventory Control and Purchasing reports and exports), each module guide lists them under Good to know.
  • Next: acceptance testing with your team on real data, module by module; confirm the production database column types before any database scripts are run there; a final security hardening step before going live (for example, password storage and a company HTTPS address).

Separate guides follow for each module: what it does, how its forms work, its reports and action buttons, and how it depends on other modules.
